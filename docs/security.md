# Sprint 1 security boundary

The browser is an untrusted public demonstration. No authenticated session, member record, invitation, or selected tenant is persisted. Browser role labels, avatar, local storage, user IDs, and organization preferences convey no authority. All authentication remains disabled in the application composition. No business endpoints or provider adapters are deployed.

The provider-neutral authentication port accepts opaque credentials only on a future trusted server. Its adapter must cryptographically verify signature, pinned issuer and audience, permitted algorithms, key rotation, expiry and token type before returning a verified assertion. Never construct assertions from request JSON. The principal resolver validates assertion shape and times, maps issuer/subject to a global identity, requires a matching server-side session, checks expiry and revocation, and caps principal lifetime at the earlier expiry. Missing credentials, malformed assertions, disabled users, missing or revoked sessions, dependency failures, and non-finite clocks fail closed. Epoch times use milliseconds. Errors carry safe codes, not provider payloads.

AuthenticatedPrincipal is a trusted application value, not a request DTO or portable authentication proof. Only a server resolver may construct one. A future endpoint resolves identity on each request and rechecks session/revocation and active membership inside mutation transactions. Integrating a provider requires server-only composition, module/bundle boundary verification, secure cookies and CSRF controls where applicable, rate limits, log redaction, and provider integration tests. No provider enablement script runs in this sprint because live authentication is explicitly excluded.

Authorization checks actor identity, active organization, active membership, requested organization, resource organization, role and permission. Unknown roles/permissions and missing states deny. Application authorization resolves the actor through the injected principal resolver and queries membership through the scoped repository; it does not accept role claims from the request. Every future protected operation must call server authorization; UI visibility is not a security boundary. Mutations must repeat the decision under a lock and validate target-level constraints.

OWNER and ADMIN have the broad permission categories. Only OWNER transfers ownership; ordinary membership mutations cannot touch OWNER. ADMIN cannot grant ADMIN or modify ADMIN peers. MANAGER manages projects/clients and approves timesheets; EMPLOYEE and CONTRACTOR track their own time and submit their own timesheets. The coarse matrix does not permit self-approval or arbitrary resource access: future resource policies must enforce those rules before endpoints exist. Billing means preparation only, never payment or payroll.

Monitoring administration is permitted only for OWNER, ADMIN, or an active MANAGER with explicit server-recorded delegation. Employee/contractor delegation never grants monitoring authority. Monitoring is OFF by default: this sprint has no collection or configuration implementation. Any future enablement requires explicit authorized configuration, visible notice, consent, retention controls, and audit; no covert monitoring is allowed. Delegation needs an audited owner/admin operation in a later sprint.

Organization rules are pure proposals using server-derived actor IDs and trusted aggregates. They are not endpoint authorization and cannot provide atomicity. Repository implementations must uphold the locking, transaction, owner, tenant, audit, and idempotency requirements in persistence-design.md. Optional lifecycle fields preserve old Sprint 0 fixtures; production authorization rejects missing lifecycle states. hasExactlyOneOwner remains a compatibility predicate, not proof of safe persisted state; validateAggregate requires explicit states, unique users, matching tenants, and an active owner for active organizations.

Invitation acceptance requires verified recipient email from the trusted provider mapping plus a server-verified digest, an active organization, current membership checks, expected version, and atomic consumption. The pure invitation state transition checks lifecycle, expiry and recipient but does not independently authenticate callers or authorize revocation. Future use cases must enforce all boundary checks. No invitation email is sent here.

Unit tests verify contracts, not live cryptography, database races, RLS, browser interaction, or production security. Architecture and secret scans are limited static guardrails; passing them is not a penetration test. Production activation remains blocked until provider and persistence adapters and their integration tests are reviewed.

# Sprint 2 offline database boundary

The browser, routes, fixtures, identity composition and disabled principal resolver remain unchanged. Persistence definitions and tests live outside browser composition in `db/`. Importing the schema does not create a connection. Architecture checks reject persistence imports in `src/` and executable Functions, reject automatic migration placement, and reject package scripts that run migrations or the disposable harness. These checks are limited static guardrails, not a complete bundler/import security proof.

## Roles and FORCE RLS

Quarantined SQL creates `hourvia_migration` and `hourvia_runtime` as NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS. Runtime never owns tables or schemas and has no membership in the migration role. A future separately managed backend login may assume only runtime; migration credentials must be unavailable to the application. No passwords, login grants or credentials are created here. Roles are cluster-wide: even an isolated database is not sufficient authorization to test role creation on a shared cluster.

All eight tables enable and FORCE RLS. The migration owner has an explicit full policy for trusted maintenance and tightly bounded SECURITY DEFINER helpers; FORCE RLS does not make a schema owner unprivileged. Runtime receives SELECT grants only on scoped tables, no provider identity table access, no DML/DDL/TRUNCATE/role grants, and an explicit false USING/WITH CHECK fallback policy. The only runtime-callable helpers are `hv_actor()` and `hv_tenant_role(uuid)`. PUBLIC function execution is revoked, helper search paths are fixed to pg_catalog/public, and PUBLIC cannot create public-schema objects, schemas or temporary tables in the target database. The migration owner remains a trusted powerful role that can change policies/triggers and must never become runtime.

Actor lookup verifies the transaction-local actor/session pair against active global user, matching unrevoked server session and live expiry. Tenant lookup additionally matches the transaction-local organization, active organization and active membership. Missing context yields no rows; malformed UUID context errors closed. Organization/membership reads are tenant scoped; session/global-user reads return only the actor/current session; invitation and audit reads require OWNER/ADMIN; idempotency reads require matching actor and tenant membership. Provider identity browsing, tenantless provisioning reads and writes have no runtime grant. There is no permissive write policy or caller-set provisioning flag.

Transaction-local settings are context, not authentication proofs. The trusted server must derive them from verified identity; UUIDs or settings supplied by a browser cannot establish authority. Anyone holding the backend SQL credential can call set_config; they are inside this trust boundary. Never expose arbitrary SQL, use a SQL credential in the browser, or use a role/settings GUC from request JSON. RLS complements server authentication and command/resource authorization; it cannot authenticate arbitrary SQL users. All pooled work uses a single connection, parameterized local settings, and COMMIT/ROLLBACK reset; uncertain connections are destroyed. Tests must also prove absent context on subsequent pool use.

## Bootstrap and commands remain blocked

Ordinary membership policies cannot authorize first organization creation or an invited nonmember. No runtime INSERT permission or tenantless RLS escape is added to solve this. Before activation, implement separate narrow audited SECURITY DEFINER/bootstrap service operations for provider/session resolution, creator-key provisioning, verified invitation lookup/consumption and own-membership listing. Fix search_path, revoke PUBLIC execution, grant only specific operations to a restricted backend login, verify trusted session and invitation/email/digest, and never accept client role/provisioning flags. Privileged routines need dedicated integration and abuse tests. These operations are contracts only in Sprint 2; the migration role is not their application adapter.

The candidate database guards enforce owner counts, lifecycle/version constraints and tenant relationships. They do not enforce the complete ADMIN/OWNER command matrix or provider verification on migration-owner writes. Runtime cannot issue those writes. Any future command grant requires command-specific authorization under tenant and live session locks, step-up/confirmation for transfer, aggregate compare-and-swap, safe idempotency replay and audit in the same acknowledged transaction. A privileged maintenance actor must uphold those protocols explicitly.

Audit updates, deletes and truncation raise even for the migration role under normal triggers; runtime cannot insert them. Superusers/owners able to alter triggers remain trusted and outside this tamper boundary. There is no monitoring, audit collection, authentication activation, endpoint or external notification. Safe audit action/target metadata and replay result allowlists, retention and operational access policy need review before live writes.
