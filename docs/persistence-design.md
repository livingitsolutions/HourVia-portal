# Sprint 2 offline persistence foundation

This sprint defines PostgreSQL/Drizzle metadata, quarantined migration candidates, transaction infrastructure, and offline tests. It does not initialize a client, provision a database, activate authentication, replace the public demo source, or expose commands. Netlify Database is the intended persistence platform. No V1/V2 source is used.

## Schema and relationships

`db/schema.ts` is the table source of truth. UUIDs are internal identifiers; timestamps are PostgreSQL `timestamptz` (UTC instants). Future adapters must convert application epoch milliseconds explicitly, set transaction time zone to UTC, and avoid implicit local date parsing. Mutable rows carry nonnegative integer versions, creation and update times; updates must advance the row version by exactly one. Audit rows are immutable and record the aggregate version instead of a mutable row version.

| Table | Relationships and constraints |
| --- | --- |
| global_users | Global UUID; active/disabled status; never keyed by email |
| provider_identities | Unique issuer/subject; global user FK; immutable provider mapping; optional provider-verified email; email is never an account-linking key |
| sessions | User FK plus composite (user, identity) FK prevents a session referencing another user's identity; expiry/revocation and version; no raw bearer material |
| organizations | Provisioning/active/suspended/closed; nonempty name; aggregate version |
| memberships | Organization and user FKs; unique (organization, user) and (organization, id); explicit lifecycle and role; active OWNER only; delegation restricted to active MANAGER |
| invitations | Tenant and id key; both inviter and acceptor use composite (organization, membership) FKs; normalized recipient; non-owner role; pending recipient uniqueness; unique SHA-256 credential digest; expiry and acceptance metadata |
| audit_events | Tenant plus composite actor membership FK; safe action, target UUID metadata, correlation UUID and aggregate version; no arbitrary payload field; update/delete/truncate rejected |
| idempotency_records | Global actor FK plus nullable composite (organization, actor) membership FK; actor/scope/operation/key uniqueness; bounded key, SHA-256 input digest; completed JSON object result; pending claims cannot commit |

The creator scope has a null tenant, operation `provision`, and scope `creator`; its result contains the created organization UUID. This claims a creator key before choosing a tenant ID and avoids SQL NULL uniqueness gaps. Other operations require a canonical tenant UUID scope and an actor belonging to that tenant. Invitation acceptance inserts the membership before completing its tenant claim. Composite FKs use restrictive deletion, never cascading tenant deletion. Target UUIDs in audit rows are descriptive metadata, not navigable resource references or permission grants; future resource references require typed composite FKs.

Invitation hashes derive from high-entropy random credentials, never email or passwords. Raw invitation links, provider tokens, assertions, session credentials, and email payloads must not enter audit or idempotency outcomes. Before activation, define a strict versioned allowlist of safe replay outcome fields and retention policy. JSON object shape alone is not sufficient output validation.

## Exactly one active OWNER

An immediate partial unique index allows at most one active OWNER per organization, including provisioning and suspended organizations. A check prevents an inactive OWNER. Deferred row constraint triggers on both organizations and memberships query the final state at COMMIT and require exactly one owner when an organization is active. These cover inserts, activation/resumption, demotion, promotion and deletes. The trigger ignores non-active organizations for the minimum count. Suspended organizations must satisfy the count before reactivation.

Every membership mutation obtains the parent organization row lock in a BEFORE trigger. Reparenting membership/user identities is rejected. Mutation guards require serializable transactions. Organization writes inherently lock their row. Future command adapters must lock organization first, then live user/session, then memberships/invitations in stable order; compare the expected aggregate version after locking and repeat live authorization. Serializable snapshot conflicts must abort and reauthorize on a bounded retry. Runtime cannot disable triggers, truncate tables, alter constraints or assume the migration role.

Provisioning reserves the creator key, creates a provisioning organization, inserts its OWNER, activates it, appends audit, and completes the idempotency result in one serializable transaction. No provisioning organization is accessible via runtime RLS. Transfer locks/reloads the active tenant, current owner and different active same-tenant recipient, compares version, demotes the existing OWNER to ADMIN, then promotes the recipient, clears delegation, advances versions, and writes audit/result atomically. Demotion first satisfies the immediate unique index; the deferred check rejects any incomplete transfer at COMMIT. A failed provisioning/transfer rolls back every write.

The SQL guards enforce counts, relationships, versions, and selected lifecycle transitions. They do not implement the whole command authorization policy. Ordinary membership commands must reject OWNER mutation/assignment, ADMIN peer changes/elevation, revoked membership reactivation, and clear delegation. Runtime has no mutation privileges or callable mutation routine in this sprint; there is no generic bypass for these missing command implementations.

## Transactions and idempotency

`db/transaction.ts` accepts an injected connection interface and performs no connection initialization. It begins serializable, validates UUID actor/session/tenant context before connection acquisition, binds transaction-local context with parameters on the same connection, calls work, and inspects the COMMIT command tag. Only an acknowledged `COMMIT` returns `committed`. A returned `ROLLBACK` returns `rolled_back`, without a value. A typed failure rolls back; exceptions roll back before retry decisions. Work must never swallow SQL errors or perform external side effects.

Only SQLSTATE 40001/40P01 allows retry, with acknowledged rollback, fresh connection/work/authorization, a stable idempotency key, and at most three attempts with bounded delay. Failed rollback destroys the connection and prevents retry. Transport failure or an unexpected command tag during COMMIT returns `commit_unknown`, destroys the connection, exposes no success value and never automatically retries. A subsequent ROLLBACK cannot establish whether the earlier COMMIT succeeded. Definite server serialization/deadlock aborts during COMMIT can retry after rollback. Other COMMIT errors are conservatively unknown, including deferred constraint failures; this intentionally favors safety over a more precise error classification.

Unknown outcomes require a new trusted connection and a scoped lookup of the same actor/scope/operation/key. Verify the canonical input digest before replaying the stored typed result. A positive committed lookup resolves the outcome. A missing result is not proof that an in-flight original request cannot still finish; reserve/retry the same key through uniqueness with a bounded wait. Never allocate a new key to bypass uncertainty. Never report successful completion from a callback return alone. The existing Sprint 1 `TransactionRunner` port is unchanged; no adapter maps unknown outcomes to its success variant.

`db/idempotency.ts` provides bounded canonical JSON hashing, claim validation and replay/conflict classification. It does not persist anything. Claim reservation uses INSERT with conflict handling under the unique key; conflict reload compares digests and either returns the identical completed result, rejects mismatched input, or waits/retries boundedly. Complete the claim with the domain writes and audit before COMMIT. Pending records cannot survive commit; completed records cannot be updated or deleted. Creator records are unavailable to generic tenant runtime reads; future narrow bootstrap services must perform resolution without opening tenantless browsing.

`db/operations.ts` records ordered obligations for provision, transfer, membership mutation and invitation consumption. Acceptance authenticates the verified recipient, checks a server-computed credential digest, locks the active tenant and invitation, rechecks pending state and expiry, rejects all existing membership conflicts (including revoked), inserts the membership, consumes the invitation once, advances versions and appends audit/result together. SQL FKs and lifecycle guards complement these checks; they cannot establish provider email verification. No notification or external delivery runs here. Any future email requires an independently reviewed transactional outbox after commit.

## Quarantine and release boundary

Candidates are ordered: `db/quarantine/000_roles.sql`, `db/quarantine/generated/20261017014340_create_identity_tenant_foundation/migration.sql`, then `db/quarantine/002_invariants_security.sql`. The generated directory also contains its Drizzle snapshot. The bootstrap administrator starts the batch, creates NOLOGIN roles, and retains `SET ROLE hourvia_migration` for table and function ownership; the last candidate resets the role. Apply a future reviewed bundle transactionally in the intended order. Only use forward changes once a migration has ever been applied; there are no down migrations.

There is no root Drizzle config, live client, Netlify migration directory, package migration command, build hook or connection during generation. `db/drizzle.offline.config.ts` explicitly outputs to quarantine. Offline generation used `drizzle-kit generate` with that config; it did not apply SQL. The schema plus custom security SQL are a single review unit: Drizzle's snapshot does not model triggers, policies or roles. Future schema changes must preserve and separately review those custom protections.

This quarantine deliberately overrides the platform's usual automatic migration placement: copying candidates into `netlify/database/migrations` activates a deploy-time execution path and is forbidden for Sprint 2. Architecture checks reject that directory and runtime persistence imports. Read [security.md](security.md), [netlify-database-assessment.md](netlify-database-assessment.md), and [persistence-operations.md](persistence-operations.md) before any future activation.
