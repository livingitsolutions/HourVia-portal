# Netlify Database adapter assessment

Assessment date: 2026-10-17. No credentials were inspected and no client or connection was initialized. The available platform guidance was compared with installed package declarations and implementation. Documentation reference: https://docs.netlify.com/build/data-and-storage/netlify-database/ and the installed package repository https://github.com/netlify/primitives/tree/main/packages/database/prod . Remote documentation was not fetched; the concrete API findings below come from installed interfaces/source, not assumed SDK methods.

| Installed package | Finding |
| --- | --- |
| @netlify/database 2.0.1 | `getDatabase(options?: { connectionString?: string; debug?: boolean })` returns a discriminated `driver: 'server' \| 'serverless'` connection; both expose `sql` and `pool`; serverless additionally exposes `httpClient` |
| Server driver | Uses the installed node-postgres pool; `pool.connect()` provides a pinned query/release client; query results include `command` |
| Serverless driver | Uses the installed Neon serverless pool for connection-pinned queries and HTTP client for independent statements; transaction work must stay on the pooled client |
| drizzle-orm 1.0.0-beta.22 | Includes `drizzle-orm/netlify-db`, `pg-core`, and schema metadata; native adapter accepts the Netlify connection via the `client` config and dispatches server connections to node-postgres |
| drizzle-kit 1.0.0-beta.22 | Offline generation with explicit config writes quarantined SQL and snapshot without a connection |

The packages were installed with the required beta tags and scripts disabled. The registry marked these beta versions deprecated in favor of release candidates; upgrades require a separate compatibility review, not an untested change of the requested adapter baseline. Production dependency audit reported zero advisories at this assessment. The full audit reported three development dependency findings (two critical and one moderate), through existing Vitest/tinypool/mocker tooling; no automatic major-version fix was applied.

The native package has no declared `db.transaction(callback)` API. Its documented transaction path is `const client = await db.pool.connect()`, followed by BEGIN, parameterized queries, COMMIT/ROLLBACK and release on that same client. `sql` alone is not a connection-affinity contract. The serverless Drizzle implementation uses HTTP outside callback transactions and a pinned pooled WebSocket client inside them; nested transactions use savepoints. Batch HTTP transactions do not supply a callback connection for setting context, locking, conditional authorization and mutation.

The installed serverless Drizzle transaction wrapper awaits `tx.execute(commit)` and returns the callback value without checking whether the command tag is COMMIT or ROLLBACK. It also starts BEGIN outside its try/finally block. A resolved callback can contain a typed failure, which the wrapper does not interpret as rollback. The node-postgres transaction path similarly must be assessed for this application's result/acknowledgement requirements before use. Merely exposing a `transaction` method does not satisfy Sprint 2.

The connection-free `TransactionConnection` contract is intentionally narrower: query results must preserve the PostgreSQL command tag and release must support discarding uncertain clients. Both installed pool client types support query and destructive release, but no production adapter is composed. A future adapter must preserve raw query result metadata, forbid mixed clients/HTTP calls, and test COMMIT loss, ROLLBACK tags, pool reuse and driver-specific error behavior. The manual disposable harness uses `getDatabase` only with an explicitly authorized local target override and rejects inherited serverless transport.

Netlify's default connection role, ability to create/manage restricted roles, ownership behavior across database branches, and a supported way to supply separate runtime and migration credentials are **unverified**. Do not assume the platform's default role is safe, switch managed credentials automatically, or initialize the default database to find out. Live activation is blocked until disposable tests prove the role arrangement and the platform's supported operational model is confirmed. No invented transaction helper, role API, connection method, provisioning call or secret-management capability is used.

## Sprint 2.1 verification (2026-10-17)

The supported [API reference](https://docs.netlify.com/build/data-and-storage/netlify-database/api/) was retrieved through its published Markdown endpoint (`api.md`). It explicitly documents `getDatabase({ connectionString })`, `pool.connect()` and BEGIN/COMMIT/ROLLBACK on one connection. The installed 2.0.1 declarations and implementation agree: server transport constructs `pg.Pool`; serverless constructs Neon Pool plus independent HTTP access. The driver depends on environment selection even with an explicit URL, so the disposable harness rejects inherited serverless transport and checks the actual driver before acquiring a client. No database client was instantiated during this review.

Verified from source/interfaces: pinned pool client lifecycle, parameterized queries, raw PostgreSQL command tags, and destructive release support. PostgreSQL transaction-local `set_config(..., true)` is the intended context boundary; actual pool reset, RLS, concurrency, COMMIT acknowledgement and transport-loss behavior remain NOT RUN. Documentation transaction examples await COMMIT but do not check its command tag; they are not proof of this application's acknowledgement guarantee. No documented guarantee was established for supported restricted role issuance, independent runtime/migration credentials, role ownership across platform branches, or migration execution with the restricted migration role. Default managed credentials must remain unused.

The adapter remains blocked. Alternatives requiring future verification are a supported separate-credential configuration using the native pinned pool and application command-tag protocol, or reviewed narrow privileged command routines with SELECT-only runtime access. Neither alternative is implemented or approved for activation. Independent HTTP statements and unchecked ORM callback transaction results do not meet the contract.

The earlier development audit is superseded by Sprint 2.1: the targeted Vitest 4.1.11 update removed tinypool and upgraded the coupled mocker packages; the post-update full audit returned zero vulnerabilities. ORM, database SDK, Vite and application dependency versions were not broadly upgraded.
